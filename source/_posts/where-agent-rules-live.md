> 「一个人带一群 agent」系列 · 第 3 篇。四篇各自独立，可以单独读。

开讲之前，先说两句我是谁。

我叫 kobin，X 上是 [@KobinFlow](https://x.com/KobinFlow)。浙大计算机毕业，在互联网行业待了十来年。现在一个人做事，写东西、写代码都离不开 agent，Claude Code、Codex、Cursor、Grok Build、Grok Bot、OpenCode、WorkBuddy，我基本都在用，每家的规矩文件也就都碰过一遍。名下还有 30 个 bot，有的找选题，有的写稿，有的写代码，有的专门验收。手上在做的产品叫点染 Dianran，一个 AI 画布。

说出来你可能不信，带 agent 最花时间的不是写 prompt，是立规矩、改规矩、给规矩挪地方。规模真不大，我自己也还是边做边学。但这一篇聊的「规矩放哪」，是我每天都在跟它较劲的事，下面的例子基本都出自我自己的仓库和 bot。

你可能也遇到过这种事。

在 AGENTS.md 里明明写了「不要用 any」，agent 还是用了。对话里交代过一次「按钮统一用主题色」，换个会话它就忘了。你把规则写得越来越长，越来越凶，大写、加粗、三个感叹号，效果反而越来越差。

我以前的第一反应是：规则写得不够清楚，再补几句。

后来想明白了，很多时候规则本身没毛病，是放错了地方。

## 规矩放哪，比规矩写什么更要紧

一个人带一群 agent，我每天其实都在立规矩。这个功能的验收标准，这个仓库的坑，这类代码的写法，我对界面的偏好。

那这些东西该写在哪？

我想了一阵，最后按两个问题来分：**这条规矩由谁执行**，人、模型还是机器？**它要管多久**，这一次、这个项目，还是我这个人？

按这两个问题排下来，正好是五个位置。从上到下，越往下越「硬」。

这就好像家里有小孩。贴在冰箱上的便利贴写「别碰插座」，管不管用全看孩子记不记得；给插座装个保护盖，就不用记了。规矩越往下放，越像那个保护盖。

## 位置一：这一次的对话里

**只管这一次的东西，就写在这一次的任务里。**

验收标准、这次不准动的文件、这次的预算上限，这些放在任务描述里最合适。放进全局规则，下次干别的活时反而碍事。

这里最值钱的一句话，是让它先问。Christoph Nakazawa（Jest 作者）在《Modern Engineering Values》里分享过他的开场白，几乎每次都差不多：

```text
I want to build X. Get context from Y and Z, make a proposal, and ask me any questions you might have.
```

翻成大白话：我要做 X，上下文去 Y 和 Z 找，先出个方案，有不明白的先问我。

我很喜欢最后半句。它把「澄清需求」这件苦差事推给了模型，我只负责回答和拍板。

Karpathy 7 月分享过另一种思路：懒得打字的时候，直接对着模型口述十分钟，让它把乱七八糟的想法整理成需求。两种做法殊途同归，都是先让模型帮你把这一次的话说清楚，再动手。

这一层还有个好处：它随任务一起消失。这次的临时约束，不会变成下个月某个 agent 莫名其妙的执念。

## 位置二：AGENTS.md / CLAUDE.md

第二层是每次开会话都会被读进去的那份文件。

它的问题是太容易写胖。什么都往里塞，技术栈、目录结构、代码风格、注意事项，写到最后几百行。

Anthropic 的 Thariq Shihipar 7 月写过一篇《The new rules of context engineering for Claude 5 models》，里面有个数字我看了好几遍：他们给 Opus 5 和 Fable 5 删掉了 Claude Code 系统提示里 80% 以上的内容，编码评测没有可测量的下降。

删了八成。没变差。

他给的建议是，这份文件主要写代码库里的坑，写模型自己看仓库看不出来的东西。技术栈它会读 package.json，目录结构它会自己翻。细节用渐进式披露，用到时再加载。

怎么判断一条该不该留？我的土办法是问自己：如果删掉这一行，agent 会不会犯一个它看代码也发现不了的错？会，就留；不会，就删。大部分「代码风格要统一」「组件要拆小」之类的话，仓库里现有的代码已经在示范了，模型会跟着走，用不着再念叨。

还有一个坑是规则打架。一边写「改完记得补文档」，一边写「不要添加注释」，模型只能猜你更在乎哪个。所以我隔一段时间会清一次。Claude Code 7 月加了 `/checkup`，能帮你找出不用的 skills、MCP 和插件，拆分过长的根目录 CLAUDE.md。

我带的 agent 不止一家，这一层还有个现实的好处：可移植。Grok Build 5 月发布时就说明了，它会直接读你现有的 AGENTS.md、skills、hooks 和 MCP 配置。所以我尽量让这份文件写成跟具体工具无关的样子，换一家 agent 不用重写一遍。

我给这一层定的标准就一句：**只写只有我知道的事。**

## 位置三：lint、类型和 CI

到这一层，执行者从模型换成了机器。

写在文字里的规矩，模型会「选择性遵守」。写进 lint 的规矩，它每次提交都会撞上，撞上了就得改。

Christoph 8 月发布了他的 oxlint 配置 v2，自己的说法是打开了很多「能让 agent 守规矩」的规则。他在原文里还有一个比喻我挺认同：跟 agent 合作，就像在大公司里不停往代码库塞没有背景的新人，lint、测试、快速验证越多，大家迭代越快。

这一层也有讲究。Christoph 的另一个要求是，工具只处理改动过的文件，不能随着代码量变大而变慢。lint 跑一次要三分钟，agent 每改一处都等三分钟，护栏就成了路障。快，是这一层能被高频使用的前提。

我给自己的规矩是**错两次就下沉**。同一类错误 agent 犯了第二次，就别再在 AGENTS.md 里加一句话了，直接看能不能变成一条 lint 规则或类型约束。Anthropic 循环指南里也是这个意思：结果不达标时，别只修这一处，要把它编码进系统，让之后每一轮都受益。

## 位置四：测试和验证 skill

第三层管的是「怎么写」，第四层管的是「怎么算做完」。

示例放在 prompt 里，agent 可能忘。比如 `formatMoney(-500)` 应该返回 `"-¥500.00"`，写成一条测试，它就忘不了，因为它跑测试时会撞上。

修 bug 我只认一个流程：先写一个会失败的测试，再修。Christoph 说这样能大幅提高模型「用正确的方法修正确的问题」的概率，否则它很容易修错地方、写错测试。

前端的验收，可以写成一个验证 skill。Anthropic 的示例叫 `verify-frontend-change`：启动 dev server，真的去点，截前后对比图，控制台零新增报错，跑一遍 Core Web Vitals，任何一步不过就从头来。

但是，有个地方要留神。

agent 很会写「一定能过」的测试。断言写得松一点，覆盖面看着很漂亮，其实什么都没测。所以测试这一层我会亲自看一眼：断言到底在断言什么。

## 位置五：记忆和参考物

最后一层，管的是「我这个人」：偏好和品味。

偏好交给记忆。Claude Code 现在会自动保存记忆，不用再手动往 CLAUDE.md 里写「我喜欢用 pnpm」。

品味交给参考物。Thariq 那篇里还有一条：spec 可以是一份测试套件、一个 HTML 设计稿，或者一套评分标准。代码本身也是很好的参考物，「照着 LoginForm 的写法做 RegisterForm」，比一段风格描述管用得多。

Thariq 还提过一个容易被忽略的点：把接口设计好，工具的参数本身就是提示。一个名字清楚、参数约束明确的函数，比一段「请注意调用时……」的说明更不容易被用错。

讲到参考物，顺带说个格式问题。给 agent 读的东西我用 Markdown，给我自己读、要我拍板的，让 agent 出 HTML。

Tim Schipper 引过 Mintlify 的测试：Claude Code 和 Codex 跑了 2400 次文档任务，读 HTML 文档平均每个任务撞到 2.23 个死链，Markdown 是 1.42，带 llms.txt 索引的 Markdown 只有 0.11。他自己也实测过输出成本。按他的测算，一份计划输出成 HTML 大约是 Markdown 的 1.9 倍，代码评审约 2.2 倍，折成钱，一份文档差个十几美分。要我做决定的东西值这个钱；spec、交接文档、循环里反复生成的东西不值，留在 Markdown。

## 有两样东西，哪层都别放

说完五层，还得补个反面。

一是太重的工具。装 MCP 之前先看它有多大。最近很火的逆向工具 REA，它的 `tools/list` 返回 139 个工具、JSON 大约 2MB，维护者自己估算光名字、描述和输入 schema 就约 16.8 万 token。这种东西常驻在上下文里，每一轮都在花钱。

二是密钥。agent 能读到的东西，都可能进模型上下文。密钥放环境变量或者工具的密钥管理里，别写进代码和文档；自动批准只开给只读或者能回滚的操作。这条是我自己的规矩，越是让 agent 长时间自己跑，越要紧。

## 拆我自己的舰队：一条规矩搬了几次家

道理讲完，我拿自己的摊子对一遍这五个位置。有的放对了，有的放错了，还有一个位置，说出来有点不好意思，是空的。

先说第二层。每个 bot 的「描述」，其实就是它自己的 AGENTS.md，每一轮都会被读进去。我在里面写得最多的，不是「怎么干」，是「不干什么」。

Codex工的描述里有一整段反职责：不做调度，不代发帖和邮件，不接短平快的杂活，搜 X、做短视频、中小编程交给 Grok Build工。Antigravity工所有稿子只交草稿。素材官那份里有一句我最看重：X写手只收它升格过的卡，别的 bot 不准直接塞给写手。

Eval验收的描述里，我写了一条退件规矩：没有成功和失败标准的需求，先退回去补标准，再验。它还被要求无数字不写，编造通过率是禁区。这条放在描述里刚刚好，因为它每一次接活都用得上。

这些都是只有我知道的事。我这支舰队怎么分工，模型看哪个仓库都看不出来，只能我告诉它。

再说第一层。点染 phase6 那一轮，Grok Bot 帮我把需求写成一份任务书交给 Codex。里面有一节叫「老板拍板（绑定）」：首要服务快速出图；视频 4K 只有模型能力表声明支持才显示；费用怎么显示、送入画布默认带什么，交给 Codex 决定，但决定和理由必须写进进度文件。

另一节叫「硬性约束」：不改 IndexedDB 的存储名，保留 MIT 许可里的版权行，不 force push，不合并 main，不碰正式站那个 Vercel 项目。这些只管这一轮，放进全局文件，下一轮做别的反而碍事。

然后，打架了。

点染是从开源项目 infinite-canvas fork 过来的。fork 过来时，上游带着一份 98 行的 AGENTS.md，写得挺认真。第一段就说：开发时优先遵循本文件，其次遵循用户当前消息。往下翻还有一条：每次写完代码，不需要检查语法，不需要执行构建，用户会自己做。

而我的任务书里，验收第一步就是 typecheck、build、跑测试。

一边说别跑，一边说必须跑，那份文件还声明自己优先级更高。这就是前面说的规则打架，只不过这回吵架的两边，一个是我，一个是上游作者。

Codex 最后跑了，typecheck 和 build 通过，17 个测试全过，听的是任务书。可它当时怎么权衡的，我翻日志没找到明说，我也不想下一次还靠它猜对。

那份继承来的文件要不要动，比如删掉「不需要执行构建」，把优先级那句换成「用户当前消息优先」，我还没决定。不动，每个新会话都在赌它猜对；动了，这份文件就从「上游的」变成「我的」，以后得我自己养着。

公平地说，那份上游文件里也有挺管用的规矩。有一条：新增或调整超时、重试次数、并发上限这类边界值之前，必须先跟用户说明。Codex 的交付记录里真就写了一句：沿用视频 7 张的收集上限，没有新增超时、重试和并发阈值。写得具体的指令，它是认真守的。

那份文件里还有一节叫「反复提醒沉淀」：同一件事被反复提醒，就补进这个文件。跟我的错两次就下沉，几乎一个意思。

第三层，坦白讲是空的。改名那一版，上游的 4 个 GitHub Actions 工作流被挪进了 `workflows-disabled` 目录，它们管的是发 Docker 镜像、发 GitHub Pages、发插件，跟点染走 Vercel 的部署对不上。结果就是，PR 上现在没有任何机器在拦，typecheck 和测试全靠 agent 自觉跑、我看记录。要不要给它补一条 PR 上自动跑 typecheck 和测试的 CI，这个我还没定，先老实承认这一层是空的。

第四层倒有一条我挺喜欢。phase6 的验收脚本里有一行断言：把整个画布项目序列化成字符串，里面不准出现测试用的那串假 API Key。「不保存 API Key」这句规矩，就这么从任务书里的一句话，变成了一行每次都会撞上的断言。

第五层是交接本。10 月 10 日总调度换了个新副本，旧的那个留下一份交接总结：我的偏好、硬规则、要重建的两条 routine。新副本的描述第一句就是，上任先读这份交接。规矩跟着文件走，不跟着哪个 bot 的记性走。

最后说一条正在搬家的规矩，省额度。

Grok Bot 的额度是按周给的，用完就停，等下周重置（[Grok Bot FAQs](https://cursor.com/help/grok-bot/faqs)）。9 月有个盯直播的定时任务撞上了周额度上限，后面十几次运行全报错；10 月 8 日又有一条定时任务因为额度失败。10 月 10 日，我让 bot 出了一份省额度方案，拟了 7 条规矩，准备追加到每个 bot 的描述里：没变化不汇报、不叫醒别的 bot，同一个操作最多重试 2 次，批量活先跑 1 到 2 个样本，等等。现在这几条已经写进了总调度的交接里，当硬规则用。

可「没变化不汇报」这条，写在描述里本质上还是冰箱上的便利贴：bot 得先醒过来、读完历史、花掉额度，才能判断出「没变化」。方案里真正想做的，是把它挪到机器那一层：在云电脑上跑一个不经过模型的检查脚本，有变化才用 webhook 叫醒 bot。这一步还没做，云电脑上连 cron 都没装。要不要在上面常驻一个调度进程，我还没想好。

你看，同一条规矩，先住在一次事故的复盘里，再搬进交接文件，下一站是脚本。

## 反方意见：AGENTS.md 也许没你想的那么灵

写到这，我得给自己泼点冷水。

ETH 苏黎世的团队 2 月在 arXiv 上发了一篇《Evaluating AGENTS.md》，专门测这类上下文文件到底有没有用。他们用了四个 agent 组合，在 SWE-bench Lite 的 300 个任务和自建的 138 个任务上跑，后者来自 12 个本身就提交了 AGENTS.md 的仓库（[arXiv 2602.11988](https://arxiv.org/abs/2602.11988)）。

结论挺扎心。上下文文件整体上没有显著提高任务成功率，却让推理成本平均涨了两成以上。LLM 自动生成的那种，成功率平均还掉了 0.5% 和 2%；开发者手写的，平均高 2.4%，但统计上也不显著。

我第一反应是有点慌，第二反应是松了口气。

因为论文里还有一句：文件里写的具体指令，agent 是照做的。提到 uv，平均每个任务用 1.6 次；没提，几乎不用。没用的主要是「仓库概览」，模型自己翻代码也能找到。这跟「只写只有我知道的事」正好对得上。

还有一个细节我记下了：手写的文件明显好过 LLM 生成的。所以我现在不会用 `/init` 一键生成一份 AGENTS.md 就算完事，生成出来的那份，我会删到只剩坑和禁区。

但它也提醒我：每一条规矩，模型都会花真金白银的 token 去执行。写得没把握的，别写。

第二盆冷水，方向正好相反。Vercel 1 月发了一篇评测：把一份压缩到 8KB 的 Next.js 文档索引直接塞进 AGENTS.md，在针对 Next.js 16 新 API 的评测上做到 100% 通过；同样的文档做成 skill，56% 的用例里 agent 压根没去调用，通过率和完全不给文档一样，都是 53%；在 AGENTS.md 里明确要求它调用 skill，也才到 79%（[Vercel 博客](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)）。

这跟我前面说的「细节用渐进式披露，用到再加载」，是正面对着干的。

我想了一阵，觉得两份研究不打架。Vercel 塞进去的，是模型训练数据里还没有的新 API 的索引，正是「看代码看不出来」的东西；ETH 测的多是 Python 仓库，模型本来就熟。也得记着，Vercel 是在测自家框架，ETH 只测了 Python。

所以我的边界是这样的。

一次性的小脚本、只活一个下午的仓库，五层用不上，任务里说一句就够了。

lint 那层有门槛：工具得快，规则得少误报，不然 agent 会花好多轮去跟规则较劲。

记忆那层最不透明，你很难 diff 它到底记住了什么。我的选择是，重要的口味写成参考物进仓库，记忆只放无关痛痒的小偏好。

## 拿走就能用：规矩放哪的速查和模板

下面这几样，是我自己在用的，改改名字就能抄。

先是一张速查表，拿到一条新规矩时对一下：

| 这条规矩是…… | 放哪 | 我的例子 |
|---|---|---|
| 只管这一次（验收标准、这次不准碰的文件、预算） | 任务描述 | 「不碰正式站那个 Vercel 项目」 |
| 每次都要说、代码里看不出来 | AGENTS.md / bot 描述 | 「X写手只收素材官升格过的卡」 |
| 写了还被违反、机器能判断 | lint / 类型 / CI | 「禁止显式 any」 |
| 定义「怎么算做完」 | 测试 / 验证 skill | 「项目数据里不准出现 API Key」 |
| 我的口味、偏好 | 记忆 / 参考物 | 「照着 LoginForm 写 RegisterForm」 |
| 密钥、自动批准 | 哪层都别放 | 放环境变量和密钥管理 |

然后是一份 AGENTS.md 骨架。只留四节，每节都是「看代码看不出来」的东西：

```markdown
# AGENTS.md

## 优先级
- 用户当前消息 > 本文件 > 代码里的既有写法。冲突时先停下问，不要自己选。

## 这个仓库的坑（看代码看不出来的）
- 例：存储名 `infinite-canvas` 不能改，改了老用户数据全丢。
- 例：API Key 只存在浏览器本地，任何导出、日志、截图都不能带出来。

## 怎么算做完
- 跑过：typecheck、build、相关测试。在交付说明里贴命令和结果。
- 改了 UI：附桌面和手机两张截图。
- 改了超时、重试、并发上限：先说明再改。

## 不要做
- 不合并 main，不 force push，不改无关文件。

## 反复提醒沉淀
- 同一件事被提醒第二次：先判断能不能写成 lint 规则或测试；写不成，再补进本文件。
```

bot 的描述，我会按这个格式写。反职责那一节最值钱：

```text
你是 <名字>，负责 <一件事>。

接单范围：<只写两三类>
反职责：
- 不做 <别的 bot 的活>，那是 <谁> 的
- 不代发任何对外内容，只交草稿
- 花钱、外发、删数据、不可逆操作，先问我
交付：结论在前，证据在后（命令、产物路径、关键结果）；做不到的写清卡点。
无任务时保持安静。
```

fork 别人的项目之后，我会先过一遍这张清单，再让 agent 动手：

- 继承来的 AGENTS.md 里，有没有声明「本文件优先于用户消息」？有，就改。
- 有没有和我的验收标准打架的条款，比如「不需要执行构建」「不用写测试」？
- 有没有我其实不认同、只是上游作者口味的规定？挑出来，删掉或标注。
- 上游的 CI 还在不在跑？关掉了的话，PR 上还剩谁在拦？
- 有没有密钥、内部地址写在文档或示例配置里？

清单我也不自己一条条翻，先让 agent 帮我过一遍。我丢给它的话是这样的：

```text
只读，不要改任何文件。通读仓库里所有 AGENTS.md / CLAUDE.md / .cursor/rules。
列出三类条款：1）声明自己优先于用户消息的；2）和「跑 typecheck、build、测试」打架的；
3）只是作者个人口味、删了也不会让你犯错的。每条给出文件路径和行号，再给一句修改建议。
```

它列出来的东西，我会挑着改，不会全盘照收。毕竟上游作者写那些规矩时，也有他自己的理由，有些我只是暂时还没看懂。

最后是一个下沉记录。每次规矩挪了位置，就记一行，几个月后回头看，哪些规矩最不老实，一目了然：

```markdown
| 日期 | 规矩 | 原来住哪 | 违反次数 | 搬到哪 | 怎么验证搬对了 |
|---|---|---|---|---|---|
| YYYY-MM-DD | 禁止显式 any | AGENTS.md | 2 | lint 规则 | CI 里故意写一个 any，看是否被拦 |
```

## 最后

写了这么多层，有点像在搞档案管理。

拿开头那条「不要用 any」走一遍。第一次发现，在任务里说一句就行。第二次又犯，写进 AGENTS.md。

写进去了还是犯，那就别再跟它讲道理了，直接在 lint 里打开禁止显式 any 的规则，让 CI 去拦。从那以后，这件事就不用我再操心了。

整个过程里，规矩的意思一个字没变，变的只是它住在哪。

我觉得整套东西归到底就是一个动作：**规矩下沉**。一条规矩刚冒出来时，先写在对话里；发现每次都要说，就挪进 AGENTS.md；发现写了还是被违反，就挪进 lint 和测试；发现它其实是我的口味，就交给记忆和参考物。

agent 一直在换，模型一直在升级，可放对了位置的规矩，会在之后每一次运行里自己生效。这可能是一个人带一群 agent 时，最划算的投资了。

你的规矩现在都放在哪一层？不妨找一条老被违反的，试着往下挪一层。
