> 「一个人带一群 agent」系列 · 第 4 篇。四篇各自独立，可以单独读。

7 月 2 日，Christoph Nakazawa 在 X 上发了一句话，大意是：大家都在搭特别复杂的 agent 配置，可很多人拿不出什么成果；Codex 加 Codiff 加人工验证，就是他现在整个开发周期需要的全部。

Christoph 是 Jest 的作者，现在在 VoidZero 做 Vite+ 这一摊。一个月前，他刚在博客《Modern Engineering Values》里晒过数字：过去 30 天推了 770 个 commit，每天平均改动约 1.5 万行代码；一年前同期是 328 个 commit，每天约 5000 行。

他自己写过，手写代码最好的一天大概 1200 行，一周也就一次。

对，一天 1.5 万行，靠的是一个 agent 加一个 diff 工具。

说实话，看到这条我是有点心虚的。

先交代一下我是谁。我叫 kobin，X 上叫 [@KobinFlow](https://x.com/KobinFlow)，浙大计算机出身，在互联网干了十年左右。现在一个人做产品，主力是「点染 Dianran」，一个节点式的 AI 创作画布；另一个是「Mood3D」，一个 Web3D 展品库。日常我在 Claude Code、Codex、Cursor、Grok Build、Grok Bot、OpenCode、WorkBuddy 之间切来切去，所以他那句话，我是对着自己的账读的。

心虚在哪？我侧栏里挂着 30 个 bot。有管调度的，有扫选题的，有写帖子草稿的，有专门验收的，还有三个分别开 Codex、Grok Build、Antigravity 的「执行工」。Christoph 说一个 agent 就够，我这边是一整支舰队。

所以这篇我不光想看懂他，也想拿他的话，回头对一下我自己的账。

## 凭什么？

我第一反应是不服气。

这半年整个行业在干什么？Claude Code 上了 dynamic workflows，一个任务能扇出几十上百个子 agent；`/goal`、`/loop`、`/schedule` 一个接一个；Cursor 9 月推出 Projects，有一个专门不写代码、只负责派活的协调者 agent。Boris Cherny 说他已经不写 prompt 了，他写循环。

人家在搭流水线，你说一把螺丝刀就够了？

更让人犯嘀咕的是他那半句「很多人拿不出什么成果」。要是真这样，问题出在哪：是配置没用，还是他手里有别人没有的东西？

7 月 31 日他还补了一刀，说现在搭 agent 的人比用 agent 的人还多。

## 先看他手里到底有什么

我把他这几个月的博客和推文翻了一遍，拼出来的工作流其实很朴素。

开场白几乎固定：我要做 X，上下文去 Y 和 Z 找，先给方案，有问题先问我。方案聊到满意再让它动手。修 bug 一律先让它写一个会失败的测试。改完用他自己做的 Codiff 让 Codex 生成一份改动走读，他看走读、看测试，不关键的地方不逐行读。

模型这块，他用 GPT-5.5，思考强度选 high。他的说法是低档质量不够，xhigh 太慢，还容易把事情搞复杂。

还有两条推文挺颠覆的。7 月 11 日，他说自己快 6 个月没花心思管理上下文了，Codex 自己会处理。9 月 11 日，他说从 GPT-5.3 左右开始，就基本没再用过 skills。

他同时推进 3 到 6 个项目，一个项目一个终端窗口。他说过，瓶颈通常在讨论和审查代码上；而在同一个项目里开好几个 agent，反而会变慢。

有意思的是，8 月 29 日他又发了一条：找一个 LLM 之前的老代码库，那种一直担心性能、内存和 bug 却没空处理的，然后放出 10 个并发 Codex 会话，「是巨大的乐趣」。我的理解是，老代码库里那些问题彼此正交，互不打架，所以能并行；新功能要他持续拍板，只能串行。这是我的推断，他本人没这么解释。

不碰上下文，不用 skills，不搭循环。这几乎是把这半年最热的几样东西全跳过了。

## 反转一：极简的只是 agent 那一层

可是再往下翻，画风就变了。

他的价值观里，有一条叫 Strict Guardrails & Fast Feedback Loops，严格护栏加快速反馈。他说跟 agent 协作，就像在大公司里不停往代码库塞没有背景的新人；lint、测试和快速验证给得越多，大家跑得越快。工具要只处理改动的文件，不能随代码量变慢。护栏和反馈的速度，决定了 agent 是 1 分钟还是 60 分钟干完活。

8 月他发布了自己的 oxlint 配置 v2，原话是打开了很多「能让 agent 守规矩」的规则。

还有一条叫 Own your Stack，核心依赖自己掌控。他说以前应用里大部分是第三方依赖，因为自己写太慢太贵；有了 agent，只要你能现实地维护，就没理由把产品核心外包出去。8 月底他把一个 20 年的 PHP 代码库交给 Codex 用现代 JS 重建，说几乎一次成功。

剥开来看，他一点都不极简。

他只是把复杂度放在了代码库里，而不是放在 agent 配置里。**护栏厚，配置薄。**这才是那句「一个 agent 就够」的真正前提。

他价值观里另外两条，也是同一个思路。一条叫 Strong Ownership：agent 放大了所有权，懂产品的人执行得更快，缺上下文的人会制造更多噪音，所以人和人之间对齐一次的代价越来越高，他预测最高效的团队会很小，两三个人，边界清楚。另一条叫 Taste：

> I have a low tolerance for bullshit, and with agents, everyone can generate a lot of bullshit all day long. Please just stop.

翻成中文大概是：我对废话的忍耐度本来就低，有了 agent，谁都能一整天批量生产废话，求你们别这样了。他说品味不只是把产品做好，更是先判断一件事值不值得花时间。

一个管人，一个管事，都在给 agent 的产出设门槛。

## 反转二：连他也会撞墙

这还没完。

9 月 6 日，他的开源赞助额度到期，换了商业账号。结果两次重置烧掉，周额度只剩 60%，他在推上问：为什么商业账号不能买重置？

还有一件事，他主力用的 GPT-5.5，OpenAI 已经公告 10 月 14 日从 ChatGPT 和 Codex 下线（API 不受影响）。这几个月 GPT-5.6、GPT-6 Astra、GPT-6 Sol 和 Luna、GPT-6.1 Sol 接连发布。

更狠的是一份行业数据。Jellyfish 今年上半年的报告里，一家典型公司的中位数用户，月花费十个月涨了 16 倍。连 Christoph 这样的重度用户都会撞上周额度，普通团队的账单只会更难看。

你会发现，他晒出来的那套工具组合，保质期也就几个月，用起来也越来越贵。

但他的价值观没跟着过期。

## 说到这儿，其实可以散了

说实话，这件事看到这里也就够了：Jest 作者用得很简单，大家别卷配置。

但有一个词，我翻来覆去还是想多说两句。

就是他价值观清单最后那一条，**Option Value**，选择权价值。它排在最后，篇幅也最短，我却觉得它是整篇的地基。

这个说法来自他更早的《Principles of Developer Experience》：对系统的任何改动，都应该为将来的改进和大变化解锁更多选择。到了 AI 语境，他补了一句很重的话：AI 从根本上缩短了大规模改动的时间，可如果你凭感觉把自己逼进了死角，可能很难、甚至根本出不来。

因为我自己是一个人做产品的，这句话戳得特别准。

先说一个看似矛盾的地方。Jellyfish 那份报告还发现，代码集中或适度集中的仓库，AI 带来的吞吐提升约 4 倍；越分散越差，最分散的一档只有 0.9 倍，用了 AI 反而略慢。

这和「小团队各管各的仓库」听着相反。我的看法是两者说的不是一回事：团队之间边界要清楚，一个系统内部别拆得太碎，agent 需要在一个地方找到所有相关代码和一套统一的约定。说到底，这也是在保留选择权：拆得太碎，以后想做一次全局改动，门就关上了。

agent 让重写变得便宜，人就容易冒出一个念头：反正以后能重写。然后心安理得地接受一个只能往一个方向走的设计。可「能重写」是有前提的。Bun 能在 11 天里从 Zig 移植到 Rust，靠的是一套现成的测试套件，那套测试，就是选择权本身。

## 拿我自己的舰队对一下账

道理看完了，轮到我自己。我把这支舰队的分工翻出来，一条条对着 Christoph 那几句话看。

先说分工，都写在每个 bot 的设定里。总调度是幕僚长，只做三件事：拆任务、一对一派给专线、追进度，只把需要我判断的事升级上来，自己不写长文、不改代码、不发帖。内容这条线，五个选题 bot 加一个 X雷达 扫信号，统一交到素材官那里，素材官是升格成选题卡的唯一出口；X写手只收升格过的卡，而且只交草稿。产品这条线，产品工程写代码和部署，Eval验收 独立验，增长实验 先定成功标准。

执行层是三个「工」：Codex工 扛中大型、多文件、要严谨的活；Grok Build工 扛搜 X 数据和中小编程；Antigravity工 扛单文件小活和文案初稿。每个 bot 的设定里都有一段「反职责」，比如不做舰队调度、不代发、没任务时保持安静。

看着挺像回事，对吧？

可账一翻就不好看了。9 月 16 日，X雷达 有一个盯直播的定时任务，半小时跑一次，跑成功 5 次之后，连续 13 次撞上额度上限报错。10 月 8 日，又有一条定时任务因为额度不够直接失败。原来我把 6 个 bot 拉在一个叫「产品×X舰队」的群里协作，10 月 10 日解散了，改成只一对一派活。

那天盘点的时候，还翻出一个早就下线、一直没删的「选题·验收」，和两个描述是空的「New Bot」。按 10 月 6 日的本地快照，总调度一个 bot 的历史数据就有约 349 MB，远远甩开其他所有 bot。所有活都从它手里过，它的上下文最先被撑胖。

于是同一天，总调度的交接文件里多了一套省额度规矩：没变化不汇报、不叫醒别的 bot；长资料存文件，只回路径；批量的活先试一两个样本；同一个操作最多重试 2 次；能不跨 bot 就不跨。

你品，你细品。Christoph 说「搭 agent 的人比用 agent 的人还多」，我自己就占了一个名额。我把这类东西叫**配置债**：每多一个 bot、一个群、一条定时任务，就多一份额度、多一层转手、多一个出错时要排查的地方，它不会自己消失。

点染改版那次更直接。我一开始让 Grok Build 从头包到尾，做到一半额度用完，报 HTTP 402；换 Codex，登录凭证被吊销，报 401；最后是 Grok Bot 的执行子代理接手，把剩下的活收了尾。进度文件里分得很清楚：前 6 个提交是 Grok Build 写的，后面的全是接手者写的，Codex 那一轮一行代码都没写成。舰队再大，额度和登录这种底层一断，那条线就停了。

但这次改版的质量没塌。我回头找原因，发现功劳不在舰队，在仓库里那份 AGENTS.md。

有意思的是，这份文件不是我写的，是从上游 infinite-canvas 继承下来的。里面有几条特别「硬」：新增或调整超时、重试次数、大小限制、并发上限之前，必须先向用户说明并取得确认；本地验收时不许关掉用户已经打开的浏览器窗口；同一个问题反复出现，就把注意事项补进这份文件。

后来 Codex 接手 phase6，它的进度文件里白纸黑字写着「未新增超时/重试/并发阈值」「未关闭用户浏览器/标签页」，IndexedDB 里那个叫 `infinite-canvas` 的存储名也原样保留。phase5 那一轮的进度文件里也有一句「存储名未改（diff 自查），LICENSE 两行版权保留」。执行者前后换了三拨，规矩一条没丢。

因为规矩在仓库里，不在某个 bot 的设定里。

这就是我版本的「护栏厚，配置薄」。bot 的设定会被换掉，会过期，会因为额度停摆；仓库里的规则、测试、lint，谁来干活都得过一遍。

回头再看哪些 bot 值得留，我的标准大概变成了两条：要么手里有独立判断权，比如素材官的升格、Eval验收 的「过不过」；要么能分摊不同家的额度，比如那三个执行工。只负责把话从一个 bot 转给另一个 bot 的，基本就是配置债。按这两条筛下来具体该砍谁，我还没拍板。

还有一处跟 Christoph 对得上。他说瓶颈在讨论和审查代码，我这边也一样：点染之前有一轮改版，agent 几天就把三个 PR 写完、部署到预览站，然后就挂在那里，等我验收、等我拍 7 个设计决定。舰队再快，最后排队的那一环还是我。

## 反方意见：一个 agent 也不总是够

说到这儿，我得替多 agent 说两句公道话，不然这篇就成了一边倒。

Anthropic 去年 6 月讲过他们的 Research 功能：Opus 4 当主 agent、Sonnet 4 当子 agent 的多 agent 系统，在他们内部的研究类评测上比单个 Opus 4 高了 90.2%。他们还发现，在 BrowseComp 这个评测上，光是 token 用量一项就解释了 80% 的表现差异（[Anthropic，2025-06](https://www.anthropic.com/engineering/multi-agent-research-system)）。

翻译一下：多 agent 很多时候赢在能烧更多 token。

代价也写在同一篇里：agent 平均比普通聊天多用约 4 倍 token，多 agent 系统约 15 倍。他们还专门说了一句，大多数编程任务里真正能并行的部分，比研究类任务少。

他们连「派几个」都写成了规则：简单的事实查找，1 个 agent、3 到 10 次工具调用就够；直接对比类的问题，2 到 4 个子 agent；只有复杂研究才上 10 个以上，而且要分清各自的职责。早期版本犯过的错，就是为一个简单问题拉起 50 个子 agent。

这条我觉得是整件事的分界线。扇出去搜信息、扫选题、做调研，多 agent 值；写同一个代码库里的新功能，单线程更稳。Christoph 对老代码库开 10 个并发会话，在同一个项目里做新功能却嫌多开会变慢，其实也落在这条线上。

另一边，Cognition 的 Walden Yan 去年 6 月写过一篇《Don't Build Multi-Agents》，核心两条：上下文要共享完整的执行轨迹，不能只传几句话；每个动作都带着隐含决定，决定一冲突结果就坏（[Cognition，2025-06](https://cognition.ai/blog/dont-build-multi-agents)）。我群聊解散之前，几个 bot 互相传话、各自理解，就是这种状况。

Anthropic 那篇附录里还有一条，我是后来才看到的：子 agent 的产出直接写进文件系统，只把一个轻量引用传回主 agent，免得层层转述走样。这跟我那条「长资料存文件，只回路径」几乎是一回事，算是殊途同归。

「护栏厚」这条也有边界。METR 2025 年那个随机对照实验里，资深开发者在自己熟悉的高质量开源仓库里用 AI，反而慢了 19%。METR 的一个解释是，标准很高、隐性要求很多的仓库（文档、测试覆盖、格式规范），AI 相对吃亏（[METR，2025-07](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)）。今年 2 月的后续估计已经转成提速，但置信区间跨过了零，METR 自己也说证据很弱（[METR，2026-02](https://metr.org/blog/2026-02-24-uplift-update/)）。

我的理解是，护栏得是写下来、机器能查的。藏在老员工脑子里的规矩越多，agent 越吃亏。

单 agent 也有它的天花板。Walden Yan 自己也承认，任务大到上下文装不下的时候，单线程会撑爆，得另想办法压缩历史。所以「一个就够」更像是默认值，不是铁律。

最后提醒一句，上面这几篇都是 2025 年的，模型已经换了好几代。Christoph 本人也只是一个样本，他是 Jest 的作者，手边还有自己写的 Codiff。他那一天 1.5 万行，我当参照，不当目标。

## 拿走就能用：薄配置、厚护栏的三件套

乱糟糟地说了不少，最后给几样能直接抄的。都是从我的仓库和 bot 设定里抽出来、去掉项目细节的版本。

第一样，仓库里的 AGENTS.md 护栏片段。思路是把「谁来干活都得遵守」的规矩写在这里，不写在某个 bot 的设定里：

```markdown
## 护栏（任何 agent、任何会话都适用）

- 先读现有代码再动手，沿用已有结构；不要顺手重构，不要改无关文件。
- 改变实际行为的边界值（超时、重试次数、大小限制、并发上限）不许静默加入；
  先说明用在哪、默认值多少、失败后怎么处理，等人确认。
- 存储名、数据结构的核心字段不改，只允许追加可选字段。
- 本地或浏览器验收用独立测试页面，不关闭用户已打开的窗口和标签页。
- 每次完成前跑：typecheck、build、相关测试；把命令和结果写进 PROGRESS.md。
- 同一个问题出现第二次，或人提醒了第二次，就把它写成一条明确规则补进本文件，
  放进最相关的章节；能写成 lint 或测试的，优先写成 lint 或测试。
- 合并进 main、force push、改计费和删数据之前，先说明影响并取得明确同意。
```

最后那条「出现第二次就写进来」最关键。它让这份文件自己长厚，而不是靠我每次在对话里叮嘱。

第二样，给 bot 做体检的清单。这是我那次盘点之后给自己列的，以后每加一个 bot、每建一条定时任务，先过一遍：

- [ ] 一句话说得清它只干哪一件事吗？说不清就别建。
- [ ] 有没有写「反职责」：哪些活明确不接、该转给谁？
- [ ] 它的产出谁来验？验的那位是不是另一个上下文？
- [ ] 交付格式固定吗？结论在前、证据在后、产物给绝对路径。
- [ ] 没有新东西时它会不会闭嘴？没变化不汇报、不叫醒别的 bot。
- [ ] 同一操作最多重试几次？撞上额度上限之后停在哪里、通知谁？
- [ ] 它能不能被一条 lint、一个脚本或者另一个现有 bot 替代？能，就别建。

最后一条最狠，也最省钱。

那到底什么时候值得拆成多个 agent？我现在的判断就三问，三个都是「是」才拆：

- 这件事能切成互相不依赖的几块吗？像扫五个方向的选题、查十个竞品的文档，可以；改同一个功能的前后端，不行。
- 每一块的产出能单独验吗？验不了，拆出去只会多一层转述。
- 这件事值那几倍的 token 吗？一个只看一次的小调研，单线程慢点也认了。

第三样，一对一派活的模板。群聊解散之后只剩一对一派活，我照着那套省额度规矩把派活消息整理成了这个格式，长资料存文件只给路径：

```text
【派活｜<任务名>】
给：<一个 bot，只写一个>
要什么：<一句话结果，能被检查>
上下文：<文件绝对路径；不要把长资料贴进消息>
完成标准：<1–3 条可检查的句子>
不许做：<发帖 / 花钱 / 删数据 / 合并 main / 改阈值>
预算：同一操作最多重试 2 次；额度或登录失败立即停，回报卡点和已试过的路径
交付：结论一句 → 证据（命令、结果、产物路径）→ 没验证到的部分
```

「预算」那一行对着的就是 9 月那 13 次额度报错。那时候定时任务撞了额度，到点还照样接着跑；现在的规矩是同一件事最多重试两次就停，回来说清楚卡在哪、试过什么。

这个模板里没有一个字在描述 bot 有多聪明，全是边界和证据。我越来越觉得，配置该薄到这个程度。

## 我从他身上抄什么

把这几层叠起来，我的结论是这样的。

我不抄他的工具清单。他用 Codex 加 Codiff，我在用 Codex、Grok Build 和 Claude 系的 agent，下个季度大概率又会变。

我抄他的分配方式：复杂度放进代码库，放进 lint、测试、类型和自己能掌控的依赖里；agent 那一层能薄就薄。

我还抄他对瓶颈的判断。他在文末写的是：以前卡在写代码，现在卡在做判断。他也自嘲过，有时候觉得自己只是在把上下文从一个 agent 会话搬到 GitHub Issue、搬到 Discord，再搬回来。

搬运这一环，工具其实在接手。Codiff 7 月的 1.9 版加了把走读和计划分享到网上、多人评论的功能；Claude Code 6 月推出了 artifacts（Team 和 Enterprise 的 beta），能把会话里的产出发布成组织内可分享、会自动更新的页面，比如 PR 走读和事故时间线。搬运能自动化，判断不行。

他对管理的看法也落在这里：管理者不能只管结果和方向，得保留领域专长，能自己动手改项目代码。他认为 Tech Lead Manager 这种角色，最适合 agent 时代的大多数管理者。

这一点放在一人公司里只会更明显。我没有同事分担判断，每条线做不做、做成什么样、能不能上线，最后都落到我一个人头上。所以我给自己定的规矩是，同时推进几条线，以我能认真验收的数量为上限，而不是以 agent 能开几个为上限。

他在原文里还说过一句，我想原样留在这里：

> I was bottlenecked on writing code, now I'm bottlenecked on exercising judgement.

工具会一直换。今天的 GPT-5.5，下周就要下线了。

但护栏、选择权、判断，这三样东西不会过期。我打算把力气花在这上面，也欢迎你一起。
