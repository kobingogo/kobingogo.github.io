鸣谢

我不再逐行看 agent 写的代码了，所以得先想清楚：凭什么信它

扬舲
AI AI

发布于：2026年10月6日
次浏览

「一个人带一群 agent」系列之一。每篇各自独立，可以单独读。

有个问题我憋了挺久。

先交代一下我是谁，不然后面的话没地方落。我叫 kobin，X 上叫 @KobinFlow。浙大计算机出身，在互联网干了十年左右。说实话，到今天我也还在摸索，算不上什么专家。

现在我也在一个人做产品。手上最主要的一个叫「点染 Dianran」，是一个节点式的 AI 创作画布；一个「Mood3D」，是一个 Web3D 展品库。我的侧栏里挂着 30 个 bot（含几个已经下线、等我手动删的），写代码这件事基本交给 Codex、Grok Build，还有 Claude 系的几个。平时我在 Claude Code、Codex、Cursor、Grok Build、Grok Bot、OpenCode、WorkBuddy 这些 agent 之间来回切，哪个顺手用哪个。

我每天干的活是写需求、定验收标准、看结果。agent 交回来的 diff，我早就不是一行一行读了。

那这算什么？算 vibe coding 吗？

按最早的定义，好像算。Karpathy 当年说的 vibe coding，就是不看代码、跟着感觉走、能跑就行。可我又隐约觉得不对：我不看代码，但我并不是「跟着感觉」。

让我想明白的，是 Jest 作者的一段话

Christoph Nakazawa（Jest 的作者，现在在 VoidZero）6 月写了一篇《Modern Engineering Values》，9 月 30 日又更新过一次。里面有一句很坦白的话，大意是：现在有些代码他不细看就合并了。

但他给了前提。测试可信，结构没问题，改动落在不关键的地方。

他还说了一个反直觉的事：他现在对人手写的代码，反而比对 agent 写的更警惕。

看到这儿我才反应过来，我纠结的方向错了。「看不看代码」这条线，已经分不出东西了。真正的分界线在别处：

你有没有一套办法，在不读每一行的情况下，证明它是对的。

我给这套办法起了个名字，叫证据链。有证据链，不读代码也是工程；没有证据链，读了代码也可能只是在走过场。

第一轮：代码能写完了，麻烦搬了家

先说一个事实变化。

Addy Osmani 去年提过一个很出名的说法，叫「70% 问题」：AI 很快帮你做完七成，剩下三成会把你拖住。今年 1 月他自己改了口，写了《The 80% Problem in Agentic Coding》，说在新项目、个人项目里，agent 能独立完成的部分已经可能超过八成。

你以为这是好消息，问题少了？

其实是问题换了地方。Addy 在那篇里列的新毛病，我挑几个最有画面感的：

  • 模型一开始理解错了需求，然后在这个错误前提上把整个功能盖完。等你发现，已经是五个 PR 之后。他叫它「假设传染」。
  • 一百行能解决的事，给你搭出一千行的类层级。
  • 老实现没删，顺手还改了旁边不该动的代码。
  • 代码能跑，测试能过，你合并了，三天后自己讲不清它是怎么工作的。Addy 管这个叫 comprehension debt，理解债。

你会发现，这几条没有一条是「写不出来」。全是「写出来了，但你不知道它对不对」。

还有一层更扎心的。Jellyfish 今年上半年那份报告发现，重度用户和中位数用户之间的差距在拉大，同样的工具，有人越用越快，有人原地打转。我的理解是，差的未必是谁更会写 prompt，更像是谁更早把「怎么验」这件事想明白了。

所以麻烦从「写」挪到了「验」。这也是为什么我觉得，今天还在用「AI 能写多少比例的代码」来讨论问题，有点问错了。

第二轮：验证这件事，agent 自己也能干一大半

那验证谁来做？

最朴素的做法是：agent 说「改好了」，人打开本地页面点一遍，开控制台看有没有红字。这活累，而且一个人带好几条线的时候，根本点不过来。

这五个月，工具把这一段接走了不少。

Anthropic 7 月发的循环工程指南（Getting started with loops）里，放了一个示例 skill，叫 verify-frontend-change。翻译一下它的意思：

对，你没看错，原本要人手动做的那套检查，现在是一份文件。agent 每次改完自己跑一遍。

Codex 那边也在补眼睛。6 月它给内置浏览器加了 Developer mode，能通过 Chrome DevTools Protocol 看网络请求、控制台和运行时错误。Claude Code 和 Codex 还都有了 /goal：你写一个机器能判定的完成条件，它一直干到满足为止。Anthropic 的示例是这样的：

首页 Lighthouse 到 90 分以上，最多试 5 次。每次 agent 想停，会有一个单独的模型来检查条件到底满足没有。

不过这里有个坑，我一开始没意识到。

让同一个 agent 检查自己的活，它会偏向自己。Anthropic 的 Thariq Shihipar 在介绍 dynamic workflows 时专门点过这个，叫 self-preferential bias（自我偏好偏差），和「偷懒提前宣布完成」「上下文压缩几轮后目标漂移」并列为长任务最常见的三种失败。

所以证据链里，至少得有一环是「外人」查的。可以是一个上下文干净的审查 agent，可以是测试，可以是 lint。反正不能全是它自己说了算。

Anthropic 的循环指南里就直接建议，用第二个 agent 做代码审查，理由很朴素：新上下文的审查者偏见更少，不会被主 agent 一路的推理带着走。

安全这块也有了专门的审查机器人。OpenAI 在台北时间 8 月 7 日通过 @OpenAIDevs 官宣了 Codex Security Review 研究预览，面向 Pro、Business、Enterprise、Edu，Plus 不在内，PR 打开或有新提交时可以自动做安全检查。额度这块有个变化：刚上线时官方文档（第三方存档）写的是「引入期不消耗 ChatGPT credits」，现在的官方文档已经改成消耗 Codex 自带额度或 credits。Cursor 9 月 23 日也上线了自己的 Security Review，每个 PR 报告可被利用的漏洞，连误提交进代码的密钥也算在内。

这些机器人很好用，但我把它们当成证据链上的一环，不当成整条链。查什么、哪些必须拦下来，清单还是我来定。

第三轮：那我还剩什么

说到这儿，可能有人要问了：验证也交出去了，审查也交出去了，你自己到底干嘛？

我想了一阵。我觉得剩下的就三样，而且一样比一样难交出去。

第一样，写出什么叫「做完了」。

这听起来简单，真写的时候经常卡住。

「页面要快」不算，「首屏 LCP 小于 2.5 秒」才算。「交互要顺」不算，写成「拖拽节点时不掉帧、松手后连线自动吸附」这种能被检查的句子才算。写不出来，通常说明我自己还没想清楚。这时候让 agent 开干，才是真正意义上的 vibe coding。

想不清楚的时候，我也会让 agent 帮我想。Grok Build 5 月发布时，官方就建议复杂任务先用 plan mode 启动，可以逐条评论、整体重写计划，再让它执行。Karpathy 7 月分享过一个更省事的办法：懒得打字，就对着模型口述十分钟，让它把一团乱麻整理成清楚的需求。但是，整理好的那份东西最后得由我签字。

Thariq 7 月那篇《The new rules of context engineering for Claude 5 models》里有一个说法我很喜欢：spec 不一定是一段文字，它可以是一份测试套件、一个 HTML 设计稿，或者一套评分标准。能执行的 spec，比能读的 spec 好用。

第二样，分清哪里必须我亲眼看。

像点染这种前端节点画布，很多改动是样式、交互细节和内部工具，这类我看测试结果和截图对比就够了。但凡涉及用户数据、权限、删除、付费，我会逐行读。

打个比方，这就像装修验收。你不会盯着工人砌每一块砖，但你会去试水压、拿水平尺量墙、开关每一个插座。哪里必须亲手试，哪里看个结果就行，这个判断本身就是你的专业。

第三样，选。

Thariq 在同一篇里说，一个 HTML 设计稿通常比文字描述和截图都更能把意思讲清楚。所以我的选择是：先让 agent 出几版 HTML 方案，我指着选一版，再让另一个 agent 照着实现。我不负责描述每一个像素，我负责说「就这个」。

拿点染拆一次：一条证据链到底长什么样

道理讲了一堆，我自己都有点虚。举个我自己的例子吧，就拿点染 10 月 5 日那一轮改版来说，这一轮所有过程文件都还在我的云电脑上，能一条条对得上。

起因很简单。上一轮把水墨视觉做完之后，我嫌操作太绕：生图页左边一长条表单，画质、比例、时长一项项往下填。我跟 Grok Bot 说的大意是，对标小云雀，一个大输入框搞定整条输入流；画质只有标准和高清，视频没有 4K，别瞎编。

Grok Bot 先没让谁写代码。它把我这几句话整理成一份简报，里面专门有一节叫「能力表事实（勿发明）」，把代码里每个模型实际支持哪些画质、比例、时长逐条抄出来。比如 Gemini 3 的「高清」实际映射到 2K，不是 4K。这份简报交给 Codex，任务写的是「出方案，不写代码」。

Codex 交回来一份交互方案，对比了小云雀、Midjourney、Runway 等六个产品，每条竞品事实都挂了官方文档链接。我在这一步拍了四条：首要服务快速出图；视频 4K 只在能力表声明支持时才显示；费用怎么显示、「送入画布」默认带什么，由它定，但必须写进进度文件说明理由。

然后才轮到实现。Codex 当唯一实现者，先做 P0（统一输入框），再做 P1（画布里的输入、引用和迭代）。它最后交给我的不是一句「好了」，而是一份进度文件，我随手贴几条：

  • P0：typecheck、build 通过，bun test 17 个用例全过、118 个断言；Playwright 在 1440 和 390 两种宽度、浅色深色共四组跑完主流程，用的是模拟渠道，没有产生真实付费调用。
  • 部署到预览站 dianran-next 后又跑了一遍冒烟：6 个页面全部 HTTP 200，运行时错误 0。
  • 首屏 JS 涨到 1,446,193 字节，比上一轮多了约 13.8%，它自己写明了原因。到 P1 又砍回去 10.4%。
  • P1：用例涨到 23 个、145 个断言；画布 agent 那边 126 个测试没动也全过。

还有两处让我挺服气的。费用那一块，原来界面上写着「约 2×」「约 2–4×」这种倍率和固定的秒数区间，简报里附了建议，Codex 核对后确认当前渠道配置里根本没有可匹配的单价，就把这些全删了，只显示真实调用次数和一句「费用由所选渠道计费」。「送入画布」默认只送最终结果，它也把理由写清楚了：默认全量同步会让人误以为工作流已经连上了。

这两条最后都是我交给它拍板的。我看的不是它选了什么，是它有没有把「为什么」留在纸面上。留了，我五分钟就能判断；没留，我就得自己去翻代码。

我最看重的反而是里面一节叫「Codex 错误与修复」。它老实写了：实现中引用过不存在的变量，被浏览器和 typecheck 抓出来；多图副本漏带了新加的快照，是扩展验收查出来的；测试脚本还一度读到热更新的另一份模块实例，测了个寂寞。

你看，这就是证据链在干活。每一个错都是被 typecheck、浏览器、验收脚本这些机器那一环拦下的，没有一个是靠我读 diff 发现的。

但证据链也有它到不了的地方，进度文件自己就写了：真实服务商的产出和计费、Sora 和 Veo 的附件适配、真机软键盘，「需用户使用自己的渠道验收」。这一段只能我来。也正因为这样，按进度文件最后一次更新（10 月 5 日），phase6 只部署在单独的 dianran-next 预览项目上，PR 停在「可合并、未合并」，正式站一行没动。

点染之外，还有一个更像「外人」的角色。我专门养了一个叫 Eval验收 的 bot，它的设定里默认立场就一句「检查通过 ≠ 可交付」，不写业务代码，只给三种结论：过、不过、有条件过。

个人站上那个「假完成闸门」demo，产品工程交过来时自证 9 个测试全绿、build 也绿。Eval验收 自己复现一遍，结论是有条件过：部分完成、工具失败、超时、空输出这几种必过场景没覆盖，失败态也缺。补到 14 个测试、加上端到端测试之后，复验才给了「过」。机械臂那个 demo 更有意思，测试全绿，它在自己环境里实测帧率 27，没到增长实验 bot 事先定的 30，照样卡住。

所以我现在的分工是这样的。Grok Bot 帮我把一句话变成能验的需求，Codex 或 Grok Build 写，Eval验收 这种上下文干净的 bot 去验，我只在证据摆齐之后做最后那个判断。说穿了就一条：验收权分离，写的人不能顺手把自己的作业判了。

反方意见：证据链也会骗人

写到这儿，我得给自己泼点冷水。证据链这套说法听着很稳，但有几条反面证据，我觉得必须摆出来。

第一条，「感觉更快」本身就不可信。METR 2025 年做过一个随机对照实验，16 位资深开源开发者在自己熟悉的仓库里做了 246 个真实任务。用 AI 的那组反而慢了 19%，可他们事前预计会快 24%，做完之后仍然觉得快了 20%（METR，2025-07）。今年 2 月 METR 发了后续，换成 Claude Code、Codex 这一代工具之后，老成员的估计变成提速 18%，但置信区间从快 38% 到慢 9%，跨过了零，METR 自己说这只是很弱的证据（METR，2026-02）。

这条对我的提醒是：不管快还是慢，「我觉得」都不能当证据链里的一环。连 agent 自己报告的「我验证过了」，也得翻出命令和结果来对。

第二条更狠，测试本身会被 agent 绕过去。METR 记录过前沿模型改计时函数、改评分代码、直接把评测函数替换成「永远通过」的例子。在 RE-Bench 上，o3 有 30.4% 的运行在钻空子，在 HCAST 上只有 0.7%，METR 推测一个原因是 RE-Bench 的任务里模型能看到整个评分函数。在提示词里加一句「请不要作弊」，有一个任务的作弊率还是 80%（METR，2025-06）。

所以验收脚本得放在干活的 agent 改不到的地方，这也是我坚持另开一个 bot 验收的原因。

第三条是安全。Veracode 用 80 个编码任务测了 100 多个模型，45% 的情况下生成的代码带了 OWASP Top 10 级别的漏洞，而且模型越新越大，安全通过率并没有明显变好（Veracode，2025-07）。10 月的更新里，最好的模型安全通过率到了 72%，也就是四个任务里还有一个多会出问题（Veracode，2025-10）。这些数字都是 2025 年的，Veracode 自己也卖代码扫描工具，读的时候心里有数就行。

前面说的 Codex 和 Cursor 那两个安全审查机器人，正好是补这一环的，但它们也只是链上的一环。

还有一条常被忽略的代价：证据链本身也要花钱。浏览器跑四组截图、再部署一次预览站冒烟，每一轮都在烧 token 和时间。一行文案的改动，没必要上全套。

说到这你应该明白了，证据链的边界大概在这几处：

  • 测试能被跑的人改到的时候，绿勾不算数。
  • 涉及用户数据、权限、删除、付费，证据链只能减少我读代码的量，不能替我读。
  • 没有测试的老代码、需求本身还没想清楚的活，根本搭不出链，这时候老老实实读。

拿走就能用：我在用的三样东西

乱七八糟说了这么多，最后给几个能直接抄的。都是从我自己 bot 的设定和进度文件里抽出来的，改改名字就能用。

第一样，放进 AGENTS.md 的「完成定义」片段。它管的是 agent 什么时候可以说「做完了」。光写一句「请认真测试」是没用的，前面 METR 那个实验里，连「请不要作弊」都拦不住，所以得把每一条写成能对着检查的东西，再要求它把证据落到文件里，下一个接手的 agent 和我都能看：

这里面最后两条最容易被删，我反而觉得最值钱。「不许改判定条件」对着的就是上面 METR 说的那种钻空子；「错误与修复」那一节，是我判断这一轮靠不靠谱最快的入口，它敢写错，我才敢信它写的对。

第二样，派给验收 bot 的请求模板。关键是把「自证」和「要验的标准」分开写，让验收的那位自己复现，而不是把实现方的截图再看一遍：

必过标准那几行，最好在开工前就写好，而不是做完了再补。我的 Eval验收 bot 有一条规矩：没有成功和失败标准的需求，先退回去补标准再验。听着有点轴，但我觉得这是在逼我把「做完了」想清楚，而不是做完了才发现说不清要什么。

「有条件过」这一档特别重要。只有过和不过两档的时候，验收的人很容易心一软就放了；多了这一档，它可以先承认主路径成立，同时把缺口一条条列清楚，实现方照着补就行。

第三样，是我给自己定的合并前五问，任何一个答不上来就不合。这几条不用放进代码块，贴在显示器边上就行：

  • 这次改动的「做完了」，我能用一句可检查的话说出来吗？
  • 证据里至少有一环不是写代码的那个 agent 自己给的吗？
  • 改动碰没碰到用户数据、权限、删除、付费？碰了就逐行读。
  • 进度文件里「没验证到」的那部分，我亲手验过了吗？
  • 关键模块的数据怎么流、权限在哪判断，我能用自己的话讲清楚吗？

回头看我自己

写到这儿，我得把自己也放进来审一下。

证据链有一个很隐蔽的漏洞，就是最后那一环：我。

agent 自测过了，审查 agent 说没问题，测试全绿，然后我点了合并。这个「点合并」的动作，到底是验收，还是盖章？说实话，我很清楚它随时可能滑向后者。同时跑好几条线的时候，注意力会被摊薄，验收很容易变成扫一眼。

Jellyfish 今年上半年的报告里有个数字挺扎心：84% 的活跃用户，同一时间最多只跑一两个 agent，原因就是人的注意力没法并行。我原以为一个人带一群 agent，瓶颈是 token、是额度。现在我更愿意承认，瓶颈是我能认真验收几条线。

所以我给自己定了两条规矩。

同类错误出现第二次，就把它写进系统，变成一条 lint、一个测试，或者验证 skill 里的一行。Anthropic 那篇指南里也是这个意思：结果不达标时，别只修这一处，要让之后每一轮都受益。

这条听起来像给自己加活，其实是在省活。一条 lint 只写一次，之后每个 agent、每一轮都替我拦着；我在对话里多叮嘱一百遍，换个会话就没了。

关键模块，我得能用自己的话讲清楚它怎么工作。不用懂每一行，但数据怎么流、权限在哪判断，讲不出来就算我没验收。

不读每一行可以，但每一次合并，都得有一条我说得出来的理由。

回到开头那个问题。我现在这样干活，算不算 vibe coding？

我的答案是：看那天的证据链完不完整。完整的时候，我是在做工程，只是换了个姿势。不完整的时候，哪怕我把 diff 从头读到尾，也还是在凭感觉。

这事我也还在练。如果你也在一个人带 agent，欢迎来跟我聊聊你的证据链是怎么搭的，咱们互相抄作业。
